# Classes and Instances

<Box>
    <NoteBox type="important">
        It is very important you know Lua before continuing.

        If you don't know Lua, our [Lua tutorial](/wiki/lua-tutorial) is a good place to start.
    </NoteBox>

    While Lua doesn't have classes built into the language, it makes them very easy to add in. We use classes *everywhere* in Kristal, and it's important to understand how they work.
</Box>

<Box>
    ## Foreword

    It's important to keep an open mind when learning about classes and instances.

    Up until now, you've only learned about procedural programming. You run one line, and then run another, and then another, and so on.

    Classes and instances are a different way of thinking about programming. Everything's in their own little world, and they can interact with each other.

    That being said, it's not *entirely* different.
</Box>

<Box>
    ## What's a Class? [classes]

    If you're familiar with **Object-Oriented Programming**, you'll know what classes are; it's the same concept here.

    A class holds a collection of variables and functions.

    It's like a template, or a blueprint. You can create multiple instances of a class, and each of those instances will do what the blueprint tells them to do.
    But each instance is unique between itself and the other instances.

    ### The Car Example

    Cars are a pretty simple concept; they have four wheels, a steering wheel, windows, and so on. That's what a car is.

    But if you were asked to describe a *specific* car, you'd start describing its color, how big it is, and so on. That's what makes it *unique* from other cars.

    There isn't just one car in the world, there are many. Almost 1.5 billion, in fact. They all have most things in common, but they are unique from each other.

    So, you can think of the concept of a car as a class, and each car in the world as an instance of that class.
    Changing the color of one car doesn't change the color of all cars, because each car is unique. That's what instances are.

    ---

    In Kristal's programming, we'd do something like the following:

    ```lua
    local Car, super = Class()

    function Car:init()
        super.init(self)

        self.color = "red"
    end

    function Car:getWheelCount()
        return 4
    end

    function Car:setColor(color)
        self.color = color
    end

    return Car
    ```

    <NoteBox type="important">
        It's important to note the functions being created using a colon (`:`) instead of a period (`.`).

        For classes, the colon is important, and basically makes a function unique per instance.
    </NoteBox>

    Making a new instance of the class is as simple as calling `Car()`. When you create a new instance, the `init` function is called. This is where you'd set up the instance.

    `self` is a special variable, which refers to the instance itself. So, setting `self.color` sets the color *of that instance*.

    `super` is also a special variable, but we'll ignore that for now.

    ```lua
    local new_car = Car() -- creates a new instance of the car class, or more simply, creates a new car.

    print(new_car:getWheelCount()) -- prints "4"
    print(new_car.color) -- prints "red"

    new_car:setColor("blue") -- sets the color of the car to blue
    print(new_car.color) -- prints "blue"
    ```

    Even though all cars are red by default, we just made a new one and changed its color to blue.

    No other cars were affected by this change, and new cars will continue to be red!

    <NoteBox type="important">
        It's very important to call instance functions with a colon (`:`) instead of a period (`.`)!
    </NoteBox>

    ### Instance Variables

    So, let's go more in-depth about variables. Each instance of something should have it's own variables, right?
    It'd be bad if every single car in the world could only have one color, which they all share.

    We can make variables unique to each instance by using `self`, which refers to the current instance.
    Creating a variable like this is called an **instance variable**, since it's unique to that instance.

    Let's look at our car example from earlier:

    ```lua
    local Car, super = Class()

    function Car:init()
        super.init(self)

        self.color = "red"
    end

    return Car
    ```

    You can see that we set `self.color` to "red". That car now has a `color` variable, which is `"red"`, and unique to that instance of the car.

    For example, if we make two cars:

    ```lua
    local car_red = Car() -- creates a new car
    local car_blue = Car() -- creates another car

    print(car_red.color) -- prints "red"
    print(car_blue.color) -- prints "red"

    car_blue.color = "blue" -- sets the color of the blue car to blue

    print(car_red.color) -- prints "red"
    print(car_blue.color) -- prints "blue"
    ```

    ... changing the color of *one* car does not affect the color of the other car.
    Again, this is because each car now has its own `color` variable, because we used `self`.

    <NoteBox type="warning">
        It's very tempting to do something like this:

        ```lua
        local Car, super = Class()

        local color -- A free-floating local

        function Car:init()
            super.init(self)

            color = "red" -- Setting the local
        end

        return Car
        ```

        However, this will **not work** as expected. `color` here is a free-floating local variable, and will only ever exist a single time.
        This means that all instances of the class will refer to the same variable, which is **not** what we want.
        And if that *is* wanted, then you should use a **class variable** instead, explained below.

        Likewise, creating a global instead, by removing the `local color` keyword, will also not work as expected. **Globals should never be used in Kristal**.

        ```lua
        local Car, super = Class()

        function Car:init()
            super.init(self)

            color = "red" -- Setting a global variable, by not defining it as local, nor using `self`
        end

        return Car
        ```

        Avoid these at all costs!

    </NoteBox>

    ### Class Variables

    This is not something that should be used too often, but you can also make variables that are shared between all instances of a class. These are called **class variables**.

    Take the following example:

    ```lua
    local Car, super = Class()

    Car.DEFAULT_COLOR = "red"

    function Car:init()
        super.init(self)

        self.color = Car.DEFAULT_COLOR
    end

    return Car
    ```

    This adds the `DEFAULT_COLOR` variable, which the class itself will have.
    This means that changing it once will change it everywhere; but you **should be very careful** when doing this.

    Most of the time, you should treat these as **static, unchanging variables**, only existing to be read, never changed.

    This is because, most of the time, you'll want to store your information elsewhere.
    For example, if you have something that creates `Car`s, and you'd like to keep track of how many cars you've created,
    put that on the class that creates the cars, as an instance variable!
    **There's no harm in having a class/instance which is only used once.**
    This concept is called a **singleton** -- a class which is only ever instantiated once, so only one copy exists.

    <NoteBox type="info">
        This is Kristal-specific, but things like `Game.world` are singletons. There's only one World instance, and it lives there.
    </NoteBox>

    ### Constructors

    Take the code we used earlier:

    ```lua
    local new_car = Car()
    ```

    This code is what's responsible for making a new instance of `Car`. When you do that, it calls the `init` function of the class. This is called a **constructor**.

    Of course, like functions, you can pass arguments to constructors. Let's say we want to make a car, but we want to set its color when we create it. We can do that like this:

    ```lua
    local Car, super = Class()

    function Car:init(color)
        super.init(self)

        self.color = color
    end
    ```

    And then we can create a new car like this:

    ```lua
    local new_car = Car("blue") -- creates a new car, and sets its color to blue.

    print(new_car.color) -- prints "blue"
    ```

## Inheritance

One of the main features of classes is their ability to inherit from other classes. This is called **inheritance**.

Basically, a "child class" *inherits* all of the variables and functions of its "parent class", but can add its own variables and functions, and even override the functions of the parent class.

Let's use another class as an example:

```lua
local Animal, super = Class()

function Animal:init()
    super.init(self)
end

function Animal:speak()
    print("...")
end

return Animal
```

Here's a very basic animal class. When you call `animal:speak()`, it will print "..." to the console. It's no animal in particular, but it's an animal nonetheless.

Now, let's say we want to make a dog class. A dog is an animal, so it should inherit from the animal class.
But dogs bark, so we want to override the `speak` function to make it bark instead.

```lua
local Dog, super = Class(Animal) -- We pass in the parent class as an argument to the Class function.

function Dog:speak()
    print("Woof!")
end

return Dog
```

Now, if we create a new `Dog` and we call speak...

```lua
local dog = Dog()
dog:speak() -- prints "Woof!"
```

This is very useful, because it shows that traits of a parent class can be shared with child classes, but the child class can dictate its own behavior.

If you have some code that expects an `Animal`, so it can call the `speak()` function on it, you can pass in your new `Dog` instance.
This is why it's so powerful; despite having the same base, each animal could have its own behavior, and code that needs animals wouldn't have to be changed whatsoever to accommodate that.

### Super

The `super` variable is a special variable which refers to the parent class. You can use it to call functions from the parent class, even if you've overridden them.

For example:

```lua
local Dog, super = Class(Animal)

function Dog:speak()
    super.speak(self) -- calls the speak function of the parent class, Animal.
    print("Woof!")
end

return Dog
```

By doing `super.speak(self)`, we call the `speak` function of the parent class, `Animal`. Then, we print "Woof!" to the console.

This'll end up printing:

```bash
...
Woof!
```

Most of the time, when you override a function, this is what you'll want to do; add behavior *on top of* the parent class's behavior, instead of replacing it entirely.
Of course, you can do that as well.

<NoteBox type="important">
    Super functions should be called with a period, not a colon! They should also take in `self` as the first argument!
</NoteBox>

<NoteBox type="warning">
    `init` functions should pretty much always call the `init` function of the parent class. Otherwise, things it requires won't be initialized.
</NoteBox>

Remember, functions can take arguments, as well. So, when you call the `super`, you must also pass in any necessary arguments.

If animal has an `init` function which takes in a name...

```lua
local Animal, super = Class()

function Animal:init(name)
    super.init(self)

    self.name = name
end

return Animal
```

... then the dog class must make sure to give the parent class's `init` function a name as well.

```lua
local Dog, super = Class(Animal)

function Dog:init(name)
    super.init(self, name)
end

return Dog
```

A child constructor does NOT need to take in the same arguments as the parent, but it must make sure to give the parent class the arguments that *it* needs.

```lua
local JoeDog, super = Class(Dog)

function JoeDog:init()
    super.init(self, "Joe") -- Since Dog's first argument is `name`, we can pre-fill that.
end

return JoeDog
```
